Date: 2026-11-18 · Reviewer agent: `architecture-reviewer` (skill `nyazek-architecture-review`) · Scope: uncommitted changes on branch `task/T-0061-t0060-decisions` against `yasir`. ## Verdict
changes required

One major finding: the currency-table lock in Q7 does not protect what it is meant to protect, and the module that holds the table cannot enforce it. The other decisions fit the modular monolith, ADR-0004 and the market-readiness rule. No new country, currency, time-zone or phone literal enters business rules. The new `cfg:` defaults follow the register's existing convention of values that the market can override. None of the decisions needs its own ADR beyond ADR-0007. Several do need their module ownership or API and event contract stated (findings below).

## Findings
| ID | Severity | Location | Finding | Recommended fix |
|---|---|---|---|---|
| F-ARCH-037 | major | ledger-reconciliation MON-8 (last sentence); ADR-0007 Q7; `AD-SET-LOCAL` | **The lock trigger is too narrow and cannot be enforced inside the module boundaries.** (a) The lock starts "once any order exists in a market". Many amounts in the currency are stored before the first order: offer prices (catalog), fixed coupons and deals (promotions), monetary `cfg:` values such as `cod.max_open_value` and `risk.hold_dual_control_threshold` (backoffice), 1P goods receipts posted to the ledger (JE for 1P stock), ad spend, and seller charges. Changing the exponent in that window reinterprets all of them (MON-1), which is the harm the decision itself names in its "Why" column. Ledger entries are financial records, and this effectively changes them destructively. (b) The currency table lives in `backoffice`, a foundation module. "Orders exist" is a fact owned by `orders`, a commerce module. Under architecture §3.1 a lower layer never calls a higher one. Backoffice could only learn it from `order.placed` events. That is eventually consistent, so a currency-table change approved in the gap before the event is consumed would still go through. | Tie the lock to a fact that `backoffice` owns. Example: the exponent and price step of a currency lock when any market that uses the currency is first enabled, or when the currency is first activated for amounts, whichever is earlier, and never unlock automatically. State that any later change is a data migration that needs its own recorded decision. Update MON-8, `AD-SET-LOCAL` and ADR-0007 Q7. |
| F-ARCH-038 | minor | ledger-reconciliation MON-4 and MON-8; configuration-register `money.price_step` | **The price step has two sources.** MON-4 makes it the `cfg:money.price_step` value (default 250 IQD), which can be edited like any `cfg:` value with an effective-from time. MON-8 makes it a column of the currency table. The new lock covers only "the price step of its currency" in the table, so the `cfg` key gives an unlocked path to the same fact. This also breaks the "No duplication" rule. | Keep one source, the currency table. Have MON-4 refer to it, and either drop `cfg:money.price_step` from the register or mark it as derived from the table and covered by the same lock. |
| F-ARCH-039 | minor | seller-accounts-kyc SEL-9; `SL-SET-VACATION`; architecture §3, §3.1 | **No module is named as the enforcer of SEL-9, and its data path is not given.** Vacation mode belongs to `sellers` (store profile). Whether a sub-order is in `PENDING_SELLER_CONFIRMATION` belongs to `orders`. Both are commerce-layer modules. §3.1 defines only downward calls between layers, so a same-layer synchronous call is not covered, and `orders` already reacts to seller state (SLA-7), which raises the risk of a cycle. SEL-5 (pickup address in use by a non-terminal sub-order) has the same gap, so this repeats a pattern rather than settling it. | State the enforcing module and its access path. Either (a) `orders` exports a query such as "count of the seller's sub-orders awaiting confirmation", `sellers` calls it, and the record confirms that `orders` never calls `sellers` synchronously; or (b) `sellers` keeps its own read model fed by `suborder.*` events and accepts a short lag. Apply the same answer to SEL-5. Record it where architecture §3.1 can point to it. |
| F-ARCH-040 | minor | seller-accounts-kyc §6.1 and SEL-9; checkout-orders state table (`AWAITING_PAYMENT`, `ON_HOLD`), SLA-1, SLA-2 | **Sub-orders already on their way to the seller are not covered.** SEL-9 checks only sub-orders that are already `PENDING_SELLER_CONFIRMATION`. Three other kinds reach that state after vacation starts: COD sub-orders `ON_HOLD` for customer confirmation (up to `cfg:cod.confirmation_window_hours`, default 24), prepaid sub-orders in `AWAITING_PAYMENT`, and orders placed before the offers' `PAUSED` status took effect. Each then waits for a seller who is away. After `cfg:orders.confirm_sla_hours` it is auto-cancelled with "counts against seller", which contradicts "without performance penalty". The Customers are kept waiting, which is the very outcome Q1 meant to prevent. | Extend SEL-9 or the vacation rules with one defined behaviour. Either count `ON_HOLD` and `AWAITING_PAYMENT` sub-orders as blocking too, or state what happens to a sub-order released during vacation (for example, it is cancelled with a seller-vacation reason that does not count against the seller, or vacation start waits until none remain). The rule should name the owning module (see F-ARCH-039). |
| F-ARCH-041 | minor | payments §7 ("Optional COD handling fee … (P1)"); scope-priorities §2.2; checkout-orders §4 step 7 and §4.1 | **The COD fee priority is still inconsistent, and the contract consequence is not stated.** Q10 makes the mechanism P0, but payments §7, the document that defines `cfg:cod.fee`, still marks it P1. The stated reason for Q10 is to avoid changing the quote engine and the ledger after launch. That holds only if the quote, order and sub-order contracts always carry the COD fee amount (with tax fields per TAX-1), even when it is 0. Checkout step 7 adds the line only "if a fee is configured". Posting rule JE-8 also does not say whether a zero amount is posted or skipped. | Change payments §7 to match Q10. State in checkout-orders §4.1 (or api-standards) that the COD fee field is always present for COD sub-orders, and is 0 while `cfg:cod.fee` is 0. State that zero-amount fee lines produce no journal line (or that the ledger accepts them). |
| F-ARCH-042 | minor | web-apps §4.3; `SF-PDP`; catalog-listings CAT-10 and CAT-12; architecture §4.2 | **Q11 needs an API and event contract it does not yet have.** The storefront (Next.js server rendering) must tell three cases apart from API data alone (ARC-7): archived (410), merged (301 to the survivor) and temporarily unavailable (200). Mobile deep links need the same answer. No product lifecycle field or survivor ID is defined for the product resource. The event catalogue has only `product.unpublished`, with no archived or merged distinction and no survivor ID. web-apps §4.2 relies on change events to revalidate edge-cached pages and to drop items from search, so a cached 200 page for a newly archived product would keep being served until its lifetime ends. | Define in the catalog contract how the product resource shows "archived" and "merged into `<id>`", and decide whether the API itself answers 410 or 200 with that status. Add `product.archived` and `product.merged` (or reason and survivor fields on `product.unpublished`, versioned per EVT-3) to the catalogue, and make them trigger edge revalidation. |
| F-ARCH-043 | minor | inventory STK-6; shared-components "Stock badge"; inventory §5 | **It is unclear which side applies the threshold, and the freshness promise cannot be met.** The badge text changed from "when the API marks the stock as low" to "at or below the threshold of STK-6". That leaves open whether clients compare the count with `cfg:inventory.low_stock_badge_threshold`, which would put a business rule in clients (ARC-6). "Never shows a count that is not the actual availability" cannot hold for product cards served from the search index (up to 60 s behind, §5) or for edge-cached page fragments. | Have the API return the low-stock count only when it is at or below the threshold, so clients never compare. Rephrase STK-6 as "the count comes from Inventory, within the freshness bounds of §5 and web-apps §4.2; it is never invented or rounded". |
| F-ARCH-044 | minor | admin-governance §3 and §5; configuration-register owners; ADR-0007 Q18 | **The backoffice approval routing cannot be derived from the documents.** §5 now says that the Super Admin edits every `cfg:` value except the commission schedule, and that financially sensitive settings change under dual control. The dual-control table names a specific approver only for tax (Finance) and the commission schedule. Every other financially sensitive value (`money`, `shipping`, `orders` "(dual control)", escrow hold, payout cycle, COD limits) falls under "Role, permission or threshold change → Super Admin (different person)", so the accountable owner role never approves. What "the owner role … reviews changes" means as a mechanism (an approval, a notification, an audit-queue item) is not defined. `backoffice` has to store an approver role for each key or namespace. | Add an approver column, or a dual-control flag with an approver role, to the generated configuration register for each namespace. Define "reviews" as a concrete mechanism. Keep the dual-control table consistent with it. Loosening any approver stays with the owner. |
| F-ARCH-045 | minor | ADR-0007 Q3 ("engineers already see queues, outbox and dead letters in the managed observability backend (ADR-0004)"); `AD-SYS-HEALTH` | **ADR-0004 does not establish this premise.** It records only "Grafana alerts on outbox age" and dead-letter alerts. Queue depth, oldest-job age, dead-letter counts and reasons, and provider circuit states are not specified as exported telemetry. Retrying or discarding a dead letter is possible only in `AD-SYS-HEALTH` (P1, Super Admin only). On-call engineers would therefore depend on a Super Admin to recover from a stuck consumer. | Either record those metrics as required telemetry in the observability work under ADR-0004, with the on-call path for retrying or discarding dead letters stated, or correct the reason given in Q3. |
| F-ARCH-046 | minor | seller-accounts-kyc SEL-6; ia-model IA-10; `SL-SET-STORE` | **Store slug derivation is not specified.** Slugs must be lower-case Latin (IA-10), but a store name may be Arabic only. The transliteration rule, the collision handling between stores with the same derived slug, and which language's name the slug comes from are all undefined. It is also not stated whether a Catalog Manager correction survives the next name change. `sellers` owns slug uniqueness and the redirect history, and both need these rules before the schema is designed. | Define the source name, the transliteration (or an ID-based fallback), the uniqueness suffix, and whether a manual correction is kept. Name `sellers` as the owner of the slug and redirect history. |
| F-ARCH-047 | note | `SL-AUTH-VERIFY`; flows FL-8; ADR-0007 Q13 | The "resume the phone step after sign-in" behaviour must be enforced by the API, not only by page routing (ARC-6, ARC-7). While the seller's phone claim is unverified, the 2FA-setup and onboarding endpoints refuse with a defined error. `sellers` reads the claim state from `identity`, which is a downward call and allowed. No change is needed if this is how the identity and onboarding contracts are written. | Carry this into the identity and onboarding API contracts. |
| F-ARCH-048 | note | support-cms CMS-7; `SF-HOME` | The home page limits (`cfg:content.home_banners_max`, `cfg:content.home_row_cards`) give "bounded payloads" only if the `content` API applies them in its responses. If clients apply them by trimming, the payload is not bounded. | State that the `content` home-page endpoint applies both limits. |

## Checked without findings
- Standing decisions: no PHP, no mobile-stack change, no new module, deployable unit, datastore or dependency. All decisions keep the modular monolith and API-first.
- Q5 and Q6 keys sit in the namespaces of their owning modules (`inventory`, `content`). The register was regenerated (140 keys). The generator change only normalises path separators.
- Q3 moves the `events` namespace owner to the Super Admin. This is consistent with Q3 and Q18.
- Q10 ledger side: account 4130, JE-8 and JE-18 already exist, and LOY-4, COM and returns already treat the COD fee. No new posting path or module dependency.
- Q13, Q14 and Q15 stay inside `identity` (claims, OTP, step-up). Q16 stays inside the seller-realm permission model (seller-dashboard §3).
- Q18 tax approval: tax rates are owned by `invoicing`, and the dual-control approval is held in `backoffice` (foundation). The call from finance to foundation is downward and follows the pattern of the manual journal entry.
- Market readiness: the new rules contain no country, currency, time-zone or phone literal in business logic. IQD defaults appear only as register defaults that the market can override.
- No decision needs an ADR of its own beyond ADR-0007. The fix for F-ARCH-037 may need one if a currency migration path is defined.
