New finding IDs continue from F-ARCH-017.

## Verdict
changes required

The revision handles the first report thoroughly. All four major findings (F-ARCH-001, -002, -004, -005) are addressed with concrete mechanisms. All minor findings and notes are resolved or properly deferred to a named task or open item. One new major finding blocks acceptance. The edge webhook buffer replays requests that API-11's 5-minute timestamp tolerance will reject, so the mechanism added for reliability-sre §4.3 does not work as written (F-ARCH-017). The other new findings are minor gaps in the new Backups and dispatcher sections, an edge-fallback claim that the static-hosting change made inaccurate, and the T-0032 gate not being encoded in the task dependencies.

## Findings

| F-ARCH-017 | major | ADR-0004, "Edge buffering of webhooks" ("The `api` still verifies the signature and timestamp on replay (API-11)"); mapping row "ARC-8, API-11 to API-14" | API-11 requires each adapter to "check a timestamp tolerance of 5 minutes", and PAY-6 repeats it for payment state. The buffer exists for origin outages, and a regional failover can take up to 4 hours (reliability-sre §4.2). Any webhook held in the queue for more than about 5 minutes fails the timestamp check on replay and is rejected. So the buffer cannot deliver the events that reliability-sre §4.3 asks for, which hurts the Order integrity SLO exactly when it matters. The ADR presents replay-time verification as the safety property without noticing the conflict. | Choose a verifiable mechanism and record it. Option 1: the Worker records the edge receipt time and authenticates it to the origin (for example an HMAC under a key shared only by the Worker and the `api`, or the origin-pull mTLS identity). The adapter then checks the tolerance against the authenticated receipt time, and still checks the signature and the event-ID replay rule. Option 2: the Worker verifies the signature and timestamp at receipt. Either option reinterprets API-11 for buffered requests, so it goes to the owner as a PRD clarification (as the first report's F-ARCH-005 fix required for the other branch). It must not be assumed. Carry the chosen rule into T-0029 (F-DOC-056). |
| F-ARCH-018 | minor | ADR-0004, "Edge buffering of webhooks" ("if the origin does not answer `2xx`, stores the raw request in Cloudflare Queues") | The Worker's behaviour is under-specified in ways that change correctness. (a) "Not `2xx`" includes `4xx`. A webhook rejected for a bad signature or as a replay would be queued and replayed indefinitely. Only timeouts, connection failures and `5xx` should be buffered. (b) The response to the provider is not stated. Once the request is durably enqueued, the Worker must answer `2xx` itself (API-12), or the provider keeps retrying in parallel with the replay. (c) The replay consumer's retry limit, dead-letter queue and alerting, and the queue's message retention compared with the 4-hour regional recovery time, are not stated. A message dropped after retention is silent loss, against the Data integrity NFR "zero silent loss". (d) Whether Worker subrequests to `api.<domain>` carry the per-hostname origin-pull client certificate that the ALB now requires (Gaps filled, F-ARCH-013) is not confirmed. If they do not, every forwarded webhook fails. | State the buffering rule (5xx, timeout or unreachable only), the Worker's `2xx` response after enqueue, the retention, retry limit and dead-letter queue with an alert, and confirm (or add to T-0032) that Worker subrequests pass the origin mTLS check. The detailed design may stay in T-0029, but these constraints belong in the decision. |
| F-ARCH-019 | minor | ADR-0004, "Backups" row "Point-in-time recovery, 35 days" ("Managed by RDS; encrypted with the database key"); row "Daily and monthly snapshots" | BKP-1 applies to all backups: "encrypted with keys separate from the production data keys and … immutable for their retention period". The point-in-time row says the opposite: it uses the database key, and RDS automated backups are not locked. Yet the BKP-1 mapping row cites the whole "Backups" section as compliant. Two details are also missing. (a) The snapshot row claims copies are "re-encrypted with the backup KMS key". For RDS, which AWS Backup does not fully manage, how copy encryption keys are chosen across accounts and regions should be confirmed, not assumed. (b) The snapshot row gives no retention, but infrastructure-devops §7 requires monthly snapshots kept for 12 months. | Either state that the 35-day point-in-time copy is a recovery convenience outside BKP-1, with the locked, separately keyed snapshots as the BKP-1 copies, and put that to the owner as a recorded deviation. Or meet BKP-1 for it too (for example AWS Backup continuous backup into the locked vault), with the key behaviour checked. Add the key re-encryption check to T-0032. State daily retention and the 12-month monthly retention. |
| F-ARCH-020 | minor | ADR-0004, "Backups" row "Third location" ("private key is held outside AWS (offline, by named owners)") and the BKP-2 sentence ("The monthly restore test (BKP-2) also restores the latest third-location dump") | BKP-2 requires the restore test to run automatically every month. A dump encrypted to a key held offline by people cannot be decrypted by an automated monthly job. So as written, either the test is not automatic or the key is not offline. The design contradicts itself, and it decides whether the third-location copy is ever proven restorable. | Pick one and record it. Option 1: encrypt each dump to two recipients, the offline recovery key and a test key held in an isolated restore account, with the test proving the decryption path and restorability. Option 2: the third-location restore is a scheduled manual ceremony with the offline key (state the cadence) while the AWS copies are tested automatically. If Option 2 departs from BKP-2's "automatically", it is an owner decision. |
| F-ARCH-021 | minor | ADR-0004, "Backups" table; Decision row "Audit trail"; Gaps filled row "Backup copy with a different provider" | Coverage gaps against infrastructure-devops §7. (a) The audit exports row ("Separate account + third location", 7 years, compliance mode) has no line in the Backups table. The ADR names the R2 lock check for the 7-year audit copy, but not the mechanism that copies the hourly audit export to the third location. (b) The KYC and document copies to the third location state no encryption, although the database dump is encrypted client-side. These are the most sensitive personal data in the system and would sit in plaintext at a third vendor, and BKP-1's key separation applies to them too. (c) The "configuration store exported daily" row of §7 is not mapped. | Add an audit-export row (mechanism, lock mode, key) and state that KYC and document copies are encrypted client-side with the backup key, like the dumps. Map the daily configuration export (for example to the same task and bucket). |
| F-ARCH-022 | minor | ADR-0004, "Backups" row "Third location" ("logical dump (`pg_dump`) of each database from the read replica") | (a) A full `pg_dump` needs read access to every module schema, including ledger, identity and audit. That is a cross-schema privilege outside ARC-4 and outside the two §3.2 exceptions. The ADR names the `dispatcher` amendment to ARC-4 but not this role. (b) A long dump on a hot-standby replica is either cancelled by recovery conflicts or forces `hot_standby_feedback` or a large streaming delay, which affects the replica that serves the search indexer and reports. It is also not said which replica (in-region or DR). | Name the backup reader role (read-only, used only by the dump task) and include it in the ARC-4 and §3.2 sentence added on acceptance. Otherwise state the replica and its conflict settings. |
| F-ARCH-023 | minor | ADR-0004, "Events and jobs across role boundaries" steps 2–5 | The wiring is right in principle but leaves gaps that `foundation.md` would otherwise fill on its own. (a) It does not say that claim, enqueue into pg-boss and mark-dispatched commit in one transaction on the `dispatcher` connection, or that the job carries the event ID as a deduplication key. That ordering is what makes delivery at-least-once without loss (ARC-5, the outbox test in architecture §8). (b) EVT-7's append-only `event_log` has no writer, schema or owning role in the design. The dispatcher is the obvious writer, but the PRD names no owner and the ADR does not either. (c) Recent pg-boss versions create per-queue tables or partitions when a queue is created, and run maintenance (archiving, deletion). If these need more than the "privileges pg-boss needs at runtime", queue creation and maintenance must happen in the migration step or under `queue_owner`. (d) The dispatcher polls about 28 outboxes to meet EVT-8 (p95 under 2 s). `LISTEN` is unavailable through a transaction-mode pooler, so polling cost belongs in the connection budget. (e) `SECURITY DEFINER` functions need a fixed `search_path` and must update only the rows they claimed (a point for the security review). | Add (a) and (e) as constraints in the section. Assign `event_log` to a schema and role, or name it an open item for T-0022. Add pg-boss queue creation and maintenance privileges to the T-0032 spike or state that they run under `queue_owner`. Note dispatcher polling in the connection budget (reliability-sre §5.2). |

## Not reviewed
- External product facts introduced by the revision were not verified against live sources: Cloudflare Queues retention and message limits, origin-pull behaviour of Worker subrequests, AWS Backup key handling for RDS copies, and pg-boss queue-creation DDL. Where they matter, the findings above ask for confirmation rather than asserting the behaviour.
- Security aspects of the new design (`SECURITY DEFINER` hardening, custody of the offline backup key, residency of Cloudflare Queues and R2 data, cosign verification at deploy time) belong to the security review. F-ARCH-023(e) and F-ARCH-028 only flag them.
- Costs were not estimated (VPC interface endpoints, Smokescreen, Workers and Queues, AWS Backup cross-region copies). Technology-stack §6 makes the estimate a Phase 1 deliverable.
- Documentation style and link correctness belong to the documentation review.
