## Verdict
approve with findings

All five earlier findings are resolved. The major F-ARCH-030 is fixed at the decision level. DNS moves to Route 53, so the switch no longer depends on the provider that is down. A CloudFront and AWS WAF standby path is pre-provisioned, the switch is a runbook step, and the degraded mode is stated. The new path is now mapped to reliability-sre §4.5, and the Risks row matches the Consequences. No new critical or major problem was found. The revision did introduce two minor defects in the standby path. First, the way the ALB admits the standby traffic is described in a way that does not work as written (F-ARCH-035). Second, the pinned mobile API certificate is not carried over to the standby path (F-ARCH-036). Both can be fixed with a sentence each, plus a check in T-0032. Neither changes the decision.

## Findings
| ID | Severity | Location | Finding | Recommended fix |
|---|---|---|---|---|
| F-ARCH-035 | minor | ADR-0004, "Edge provider outage" point 2 ("The ALB accepts the standby path through a separate listener rule that requires the CloudFront origin prefix list and a secret origin header; that rule is disabled until the switch"); "Gaps filled" row "Load balancer reachable only from the edge" (ALB mutual TLS for Cloudflare authenticated origin pulls); T-0032 rows | The admission mechanism does not work as written. (a) ALB mutual TLS is set on the listener, not on a listener rule. A new rule on the existing HTTPS listener still requires a Cloudflare origin-pull client certificate during the TLS handshake, which CloudFront requests will not present. (b) A managed prefix list such as the CloudFront origin-facing list is matched in a security group, not in a listener rule. The ALB's security group currently admits only Cloudflare ranges (INF-3), so CloudFront traffic is dropped before any rule runs. As written, the switch in point 3 ("enable the standby listener rule and change the Route 53 records") would fail during the incident it exists for. (c) A Route 53 apex record cannot be a CNAME, and a Route 53 alias cannot point to Cloudflare. So any apex host behind Cloudflare needs a stated approach, such as a redirect to `www`. None of this is in the T-0032 spike list. | State the correct design: a separate HTTPS listener (another port, or a second ALB) without mTLS verification, which accepts only requests carrying the secret origin header and is kept disabled or unreachable until the switch. Add a security-group rule for the CloudFront origin-facing prefix list, pre-created or added by the runbook. State how apex hosts are handled. Add "standby path end-to-end, including ALB admission and apex records" to T-0032. The section 4.4 drills then exercise the path. |
| F-ARCH-036 | minor | ADR-0004, "Edge provider outage" points 2–4; Decision row "Mobile API certificate"; MOB-10 | `api.<domain>` is served with a custom certificate whose keys Nyazek holds, and the mobile apps pin the current and backup public keys (MOB-10). The standby CloudFront distribution must present a certificate built on one of those pinned keys. If it uses an ordinary ACM-issued certificate, every pinned app fails TLS to the API during the switch. The degraded-mode list does not mention this. Today the impact is limited because the mobile apps ship after launch, but the standby path must be ready before they do. | Add one sentence: the standby distribution for `api.<domain>` uses the same Nyazek-held key pair, imported into ACM (in `us-east-1` for CloudFront), and is kept in step with the Cloudflare certificate on rotation. Alternatively, list "mobile API unavailable while switched" in point 4 for the owner to accept. |

## Not reviewed
- External product facts were not checked against live sources. These include Cloudflare partial (CNAME) setup plan requirements, CloudFront origin mutual-TLS support, ALB listener and security-group behaviour, and ACM certificate import for CloudFront. F-ARCH-035 and F-ARCH-036 rest on documented AWS behaviour as generally known; T-0032 should confirm it.
- The AWS-side zero-trust path for Admin during a switch is left to T-0028. Its choice, and any new AWS service it adds, belongs to the security review and the owner.
- Security aspects remain with the security review. These include custody of the receipt-signing and payload keys, the secret origin header, and the absence of Turnstile and bot management while switched.
- Settled points from the earlier reports were not re-opened. Documentation style and link correctness belong to the documentation review.
