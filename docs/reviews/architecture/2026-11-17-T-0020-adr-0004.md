# Architecture review — T-0020: ADR-0004 Technology stack
Date: 2026-11-17 · Reviewer agent: `architecture-reviewer` (skill `nyazek-architecture-review`) · Scope: `docs/adr/0004-technology-stack.md` (status Proposed), checked against `docs/prd/06-platform/*.md`, `docs/prd/07-clients/web-apps.md`, `docs/prd/07-clients/mobile-flutter.md`, `docs/prd/07-clients/design-system-ui-workflow.md` (rule coverage only), `docs/prd/00-governance/open-decisions.md`, ADR-0001, ADR-0002, ADR-0003, `tasks/02-architecture/README.md` (row T-0020) · Follows up: —

Finding IDs use the `F-ARCH-NNN` prefix defined in `docs/reviews/README.md`. This is the first architecture report, so numbering starts at 001.

## Verdict
changes required

The ADR is well structured. Every numbered rule ID in `06-platform` (ARC, EVT, API, DAT, INF, ENV, REL, BKP, CAP, INC) and in the two client documents (WEB-1..7, MOB-1..11) appears in the requirement mapping. The standing mandates hold: no PHP, Flutter, a modular monolith, and Claude as the only agent. The Node.js 26, NestJS 12, Kysely 0.29 and pg-boss 12 floors are internally consistent. RDS Multi-AZ meets the availability-zone recovery objectives in reliability-sre §4.2 (RPO 0 through synchronous standby, automatic failover well inside 15 minutes). The owner decision is pending, so the status Proposed is expected and is not a finding. Four major findings block acceptance. Two concern feasibility: the backup chain to the third location, and the outbox/pg-boss design against ARC-4. Two concern the completeness of the mapping: the NFR rows, and the queueing of webhooks at the edge.

| F-ARCH-001 | major | ADR-0004, Requirement mapping row "BKP-1, BKP-2"; Gaps filled row "Backup copy with a different provider" | The BKP-1/BKP-2 mapping ("RDS continuous archiving and snapshots copied cross-region and to the third location") cannot be built as written. Amazon RDS gives no access to WAL files. RDS snapshots can only be copied within AWS, and the RDS export to S3 writes Parquet files that cannot be restored as a database. So infrastructure-devops §7 ("copied to DR region and to the third location") has no named mechanism for the third location. BKP-1 immutability is not addressed either. RDS automated backups and manual snapshots are not locked against deletion; that needs something like AWS Backup with Vault Lock in compliance mode. The ADR also does not say which key encrypts the third-location copy. The R2/B2 lock spike covers only the bucket, not how a restorable database copy gets there. The analytics database (also in the §7 row) is not mentioned. | Name the mechanism per copy. In-AWS copies: for example AWS Backup with cross-region and cross-account copy and Vault Lock in compliance mode, using the backup KMS key. Third location: for example a scheduled, stateless logical dump (from the replica) that is encrypted client-side with a backup-only key before upload to R2/B2 under lock. State the resulting third-location recovery point (for example daily) and the restore time. Make sure BKP-2's monthly restore test also covers a restore from the third location. Cover the analytics database too. |
| F-ARCH-002 | major | ADR-0004, Decision row "Jobs and events" ("Enqueue inside the business transaction (ARC-5)"); mapping row "ARC-5, EVT-5 to EVT-8"; mapping row "ARC-2, ARC-4, DAT-1" | pg-boss keeps its jobs in its own shared schema. If a module enqueues inside its business transaction under its own database role, that role needs write privileges on a schema it does not own. ARC-4 forbids this ("privileges only on its own schema"), and architecture §3.2 lists exactly two cross-schema exceptions (ledger posting, audit append). The outbox dispatcher has the same problem: it has to read and update every module's outbox table (ARC-5 puts the outbox in the module's schema). The ADR adopts the PRD wording (technology-stack §3.2) without resolving the conflict, and `foundation.md` (T-0022) would inherit it. | Decide in this ADR (or in a linked ADR) how events and jobs cross the role boundary. One option: the business transaction writes only to the module's own outbox and job-request tables, and a dedicated dispatcher role reaches them through execute-only functions granted per module (the same pattern as §3.2), then enqueues into pg-boss under its own role. The other option is for the owner to approve a third named exception, with the matching change to architecture §3.2. Name the pg-boss schema owner and runtime role. |
| F-ARCH-003 | minor | ADR-0004, Gaps filled row "Connection pooling …"; mapping row "ARC-2, ARC-4, DAT-1"; Consequences (spike) | RDS Proxy covers only part of what infrastructure-devops §6 and reliability-sre §5.2 require. (a) RDS Proxy sets connection limits per proxy and target group (`MaxConnectionsPercent`), not per database user, so the "connection budget defined per module pool" (§5.2) cannot be enforced at the proxy. It would have to be enforced by client-side pool sizes in every task. (b) Each of the roughly 28 module roles needs its own registered credential (one Secrets Manager secret per role, or IAM authentication), which adds operational surface. (c) The spike is scoped to "pinning under Kysely and pg-boss". It should also cover the other known pinning triggers: session-level `SET`, named prepared statements, session advisory locks, `LISTEN`, temporary tables. It should also cover the shared-transaction calls in §3.2. (d) The mapping routes tolerant reads to a read replica (NFR row "API and search latency"). Whether RDS Proxy can front a read replica of RDS for PostgreSQL (as opposed to an Aurora reader) is not stated. | Widen the spike's question list to (a) through (d). State in the gap row that per-module connection budgets are enforced by client pool sizes (with either pooler). Record how replica connections are made. |
| F-ARCH-004 | major | ADR-0004, Requirement mapping (claim at line 100, "Every rule in the platform and client documents maps to a component"; NFR rows) | The NFR table in reliability-sre §1 is only partly mapped. Either map UI-1 to UI-4 (Storybook, Playwright visual tests, token generator) or narrow the claim to the documents actually covered. |
| F-ARCH-005 | major | ADR-0004, Requirement mapping (missing); reliability-sre §4.3 | reliability-sre §4.3 requires that "payment webhooks received by the edge during the outage are queued and replayed". No component maps to this. On the chosen edge it would need edge compute plus a durable queue (for example Cloudflare Workers with Queues), which are Cloudflare products beyond those the PRD and the ADR name (CDN, WAF, bot management, rate limiting, Turnstile, DNS, zero-trust). | F-ARCH-006 | minor | ADR-0004, Requirement mapping and Decision rows "Mobile", "Repository and delivery", "Testing and security tooling" | Platform and client requirements without a rule ID are not mapped, though the T-0020 criterion says "every PRD platform requirement": synthetic checks from outside the cloud, including probes in Iraq (reliability-sre §3); per-pull-request preview environments, which need datastores (infrastructure-devops §3); OpenTofu remote state with locking and encryption, and daily drift detection (§4); account budgets and alerts (§8); bundle-size and Lighthouse CI budgets (web-apps §7); the token generator from `tokens.json` to CSS, Tailwind and Dart (design-system §2); Fastlane and FVM, which mobile-flutter §2 and §7 name; the licence check and infrastructure-as-code scan in SEC-25. | Add these to the mapping, or delegate each one explicitly to the guide task that will choose it (as was done for the boundary-lint tool and T-0041). |
| F-ARCH-007 | minor | ADR-0004, Verification row "pg-boss" ("schema migrates automatically on start") | The ADR presents pg-boss's automatic schema migration on start as a plain fact. That behaviour conflicts with REL-4 (migrations run as a separate pipeline step, with a lock and a timeout, before the new version starts) and REL-3 (expand/contract). It also requires the runtime role to hold DDL rights, which works against least-privilege roles (ARC-4). | Record that pg-boss runs with automatic migration disabled at runtime. Its schema upgrades run in the REL-4 migration step under the migration role, and a pg-boss major upgrade is treated like any other expand/contract migration. |
| F-ARCH-008 | minor | ADR-0004, Gaps filled rows "Controlled egress allow-list (INF-4)" and "SSRF-safe proxy" | (a) The stack adds outbound destinations beyond the INF-4 list (PSP, courier, SMS, email, push): Grafana Cloud, Sentry, R2/B2, ClamAV signature mirrors, Google Maps (P1), the status-page API. AWS service endpoints (ECR, Secrets Manager, KMS, S3) are also needed and are better reached through VPC endpoints. None of this is stated. (b) The only alternative given for AWS Network Firewall is "NAT plus security groups only (cannot filter by domain)", which is a straw man. Smokescreen, already chosen, supports domain allow-lists per role and could enforce the whole egress allow-list as one stateless component. Network Firewall has a fixed hourly cost per availability-zone endpoint, paid in production and again in staging (ENV-3 mirrors the topology). Checklist item: proportion. | List the extra egress destinations and the VPC endpoints. Add "single egress proxy (Smokescreen) for all outbound traffic, with NAT locked to the proxy" as a real option with its trade-offs (domain filtering versus layer-3/4 inspection, cost), and let the owner choose. |

| F-ARCH-013 | minor | ADR-0004, Gaps filled row "Load balancer reachable only from the edge (INF-2, INF-3)" | An allow-list of Cloudflare address ranges alone lets any Cloudflare customer's traffic reach the origin.
